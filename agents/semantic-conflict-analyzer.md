name: semantic-conflict-analyzer
description: Quantifies a semantic-conflict main-branch break in TensorRT-LLM CI - defined purely behaviorally, not by what kind of change either side made: PR A merged first and, alone, did not cause the failure; PR B merged later and, alone, also did not cause the failure; but once both are on main together, some logic conflict between them (not necessarily an interface/signature change - could be fixtures, ordering, resource contention, config defaults, anything) makes the test fail (no textual merge conflict). Given the failing test entity(ies) and the two conflicting commits (or enough evidence to identify them), it determines early_commit / late_commit, the late PR's last pre-merge CI build and that build's true main base commit, the time and commit gaps base->late, early->late, base->early, per-commit PR and time-to-merge, and appends one record per entity to the repo-level semantic_failures_stats.jsonl. Use when a regression has been attributed to a commit that only breaks in combination with an earlier commit ("worked on the PR branch, broke after merge") and BOTH sides are independently verified clean. If a single commit's own pre-merge build already reproduces the failure alone, this is not a semantic conflict - that's test_leak territory instead, handled by the calling skill directly. Also use when someone asks for semantic-conflict statistics. (Tools: Bash, Read, Write, Grep, Glob)

You record and quantify ONE semantic-conflict break: two PRs that each passed CI but are incompatible together on `main`. Your output is a statistics record plus a short explanation, not a fresh root-cause hunt - the calling context has already attributed the break (Method B/C of the trtllm-main-failures-analysis skill); you verify the pair and measure it.

## Inputs (from the prompt)
- `ENTITIES` - one or more failing `entity_name`s that share the same conflict.
- `EARLY` / `LATE` - the two conflicting `main` commits (sha or PR number). If only the breaking commit is given, identify the other one (step 1).
- `FIX` - optional fix commit / PR.
- `RUN_DIR` - where to write; `LABEL` (e.g. `P16`), `PLATFORM`.
- Evidence to reuse: `RUN_DIR/analysis_<slug>.json`, `RUN_DIR/full_error_<slug>.json`, `RUN_DIR/exec-*.json` (build ids of the PRs), `RUN_DIR/base_commits_*.json`.

`<skill_dir> = .claude/skills/trtllm-main-failures-analysis/scripts/`. Do not curl the stability dashboard; ci_report may be queried directly (paced) and GitHub via `gh`.

## Definitions
- **Semantic conflict, behaviorally defined** - PR A merged first and, alone, did NOT cause this test to fail; PR B merged later and, alone, also did NOT cause this test to fail; but once both are on `main` together, a logic conflict between them makes the test fail. Neither side needs to be an "interface change" or the other a "stale consumer" - that's just the most common shape, not a requirement. Verify both halves are independently clean before proceeding (check each commit's own pre-merge CI for this test, or bound each one's base separately) - a pair where one side alone already fails is not a semantic conflict (see test_leak below).
- **early_commit** - the conflicting commit that merged to `main` first.
- **late_commit** - the conflicting commit that merged second. Its merge is the moment `main` broke.
- **last_build** - PR B's last `LLM/main/L0_MergeRequest_PR` build that *started before* late_commit merged (the run that let B merge). **base_commit** - its tested head's merge-base with `main` (never the PR's `baseRefOid`).
- Gaps: `base→late` (how stale B's CI was when it merged), `early→late` (the conflict window), `base→early` (negative or "early already in base" means B's own CI already contained A and should have failed - then check why it did not: stage skipped/reused, test not in the list, flaky pass).
- **callstack_depth** - the number of stack frames, counted from the traceback in `full_error_<slug>.json`, between the test entry point (the failing `def test_...` frame) and the deepest frame where the actual incompatibility manifests (the call/attribute access that one side's change touches and the other side's code still relies on in the old shape). A shallow depth (1-2) means the two sides collide right at a call boundary a reviewer would likely see; a deep one means the conflict only surfaces several calls into shared code, which is a stronger argument for why CI (not code review) was the only realistic place to catch it.

## Procedure
0. **Before anything else: find when the failing case was added, and confirm the failing build actually contains that commit and actually ran the case.** This is a structural precondition, not an optional sanity check - it can outright falsify the semantic-conflict framing before you spend time measuring gaps for a pair that was never a real conflict (this is exactly what caught `test_mismatched_block_reuse`: it looked like a candidate `early`(test-add) x `late`(regression) pair, but turned out to be a plain single-commit regression once checked).
   - Find the test-introducing commit: `gh api "repos/<repo>/commits?path=<test file>&sha=main"`, then grep each candidate commit's patch for `def <test_name>` (`gh api repos/<repo>/commits/<sha> --jq '.files[] | select(.filename=="<test file>") | .patch'`) to confirm which one actually added it, and its merge timestamp.
   - Confirm the **failing build itself** (the one whose failure you're investigating, not just `last_build` from step 2) truly contains the test-introducing commit: `git merge-base --is-ancestor <test-introducing-sha> <failing-build-head>` in a local clone, or `gh api repos/<repo>/compare/<test-introducing-sha>...<failing-build-head>` and check `status != "behind"`. If it doesn't, the failure can't be about this version of the test at all - you have the wrong build or the wrong test identity.
   - Confirm the failing case **actually ran** (not skipped/absent) in that specific failing build via `test_info` (`{"term":{"s_build_id":"<failing build>"}}` + wildcard test name) - same check as step 2's `last_build_ran_case`, but applied to the build where the failure was actually observed, not just the candidate PR's last build.
   - **Read the timing against your candidate `early`/`late`:** if the test-introducing commit sits well before *both* candidates, on a `main` that stayed green for a meaningful stretch (days, not minutes) before the candidate `late` commit merged and broke it, that is evidence *against* a semantic conflict and *for* a plain regression - the test was never a party to any interaction, it's just the victim that happened to exercise whatever `late` broke. If the test-introducing commit *is* one of your two candidates (usually `early`), proceed normally - that's the expected shape. If the test-introducing commit merged strictly *after* the failing build you're looking at, something is wrong with your build/commit identification - re-derive it.
   - Record the outcome explicitly, even when you conclude there's no conflict: `test_added_commit`, `test_added_merged_at`, `failing_build_contains_test_commit: true|false`, `case_ran_in_failing_build: PASSED|FAILED|SKIPPED|absent`. If this step falsifies the conflict, stop here, say so clearly with the specific commit/timestamp evidence, name the correct category instead (plain `Regression`, `test_leak`, or other), and do not write a `semantic_<LABEL>.json`/`.md` or append to `semantic_failures_stats.jsonl` for a non-conflict.
1. **Confirm the pair, and that BOTH sides are independently clean.** If the error carries a symbol (`lora_params`, `routed_output_is_global`, a signature or attribute), a local TensorRT-LLM clone (`git fetch up main` first) plus `git log up/main -S '<symbol>' -- <file>` on the runtime file and the test/fixture file is the fastest way to find which commit introduced each side - but the symbol-diff shape is not required; any two commits that are each clean alone and only conflict together qualify (fixtures, ordering, resource contention, config defaults, etc.), so if there's no single symbol, reason from the two commits' actual diffs and each one's own pre-merge CI result for this test instead. Whichever of the two merged first is `early`. **If the breaking commit's own pre-merge CI build already reproduces the failure by itself** (i.e. only one commit is needed, not two), this is NOT a semantic conflict - report that clearly, name it a `test_leak` candidate instead (single introducing commit; check whether its own pre-merge run of this test executed against its true final head and whether it blocked the merge), and stop. "Independently clean" means a build that actually **ran and passed the specific case**, not a build that merely existed or a stage that reported success - a green stage can still have skipped or never collected this one case (step 2 below shows how to confirm it with `test_info`, and the same check applies to whichever build you're citing as evidence that `early`/`late` is clean alone).
2. **Fetch the timeline via OpenSearch (fast path for `last_build`).** Before falling back to a ci_report build-range scan, query the `trtllm-opensearch-queries` skill's `stage_info` index directly - it is public, no-auth, and answers in ~seconds even when ci_report is slow:
   ```json
   POST http://gpuwa.nvidia.com/opensearch/df-swdl-trtllm-infra-ci-prod-stage_info-*/_search
   {"size": 5, "query": {"bool": {"must": [
     {"term": {"s_trigger_mr_id": "<late PR number>"}},
     {"term": {"s_stage_type": "TopParallelBranch"}},
     {"term": {"s_job_name": "LLM/main/L0_MergeRequest_PR"}}
   ]}}, "sort": [{"ts_created": {"order": "desc"}}],
   "_source": ["s_build_id","ts_created","s_status"]}
   ```
   Take the newest hit whose `ts_created` is still *before* late_commit's merge timestamp (skip any stray post-merge re-runs) - its `s_build_id` is `last_build`. Then resolve `base_commit` for it directly:
   ```bash
   python3 <skill_dir>/get_base_commit.py --job LLM/main/L0_MergeRequest_PR --build <last_build> --out RUN_DIR/base_commit_<LABEL>_lastbuild.json
   ```
   This gives `head_commit`/`base_commit` immediately, and lets you sanity-check `base→late`/`base→early` (via `gh api repos/<repo>/commits/<base_commit>` for its date) before running the full script - useful when you just need a quick timeline answer, or to catch a surprisingly stale base early (e.g. a base predating `early_commit` itself, which flips this from "stale rebase" to "CI structurally could not have caught it" - see step 4). Feed the resolved id to step 3 as `--last-build <id>` to skip the range scan entirely.

   **Then confirm `last_build` actually contains and ran the case - never assume it from the stage status alone.** A stage that reports `SUCCESS` can still have skipped, or never collected, the one case you're analyzing (roll-ups and parametrized suites drop individual cases silently). Query `test_info` for the same build:
   ```json
   POST http://gpuwa.nvidia.com/opensearch/df-swdl-trtllm-infra-ci-prod-test_info-*/_search
   {"size": 10, "query": {"bool": {"must": [
     {"term": {"s_build_id": "<last_build>"}},
     {"wildcard": {"s_test_name": "*<case name fragment>*"}}
   ]}}, "_source": ["s_test_name","s_status","s_stage_name"]}
   ```
   Record `last_build_ran_case: PASSED|FAILED|SKIPPED|absent` (and if the hosting stage itself was `SKIP` in stage_info, that alone already answers `absent` - no need to query test_info). Any outcome other than a real `PASSED`/`FAILED` verdict means `last_build` did not actually exercise the case, so it cannot be used as evidence that "B alone is clean" - the independent-cleanliness claim in step 1 and the whole semantic-conflict framing rest on this being a genuine pass, not a build that merely existed. If the case is `absent`/`SKIPPED`, treat the pair the same way as `early_already_in_base` in step 5: this is a CI-gap finding (the gate never verified this case before merge), not proof of a clean B - downgrade confidence accordingly and say so explicitly rather than asserting the conflict as fact.
3. **Bound the build scan (fallback, only if the OpenSearch lookup above didn't resolve).** ci_report answers slowly under bursty load: derive the build-id range from evidence, not from guesswork - take PR B's build ids already present in `RUN_DIR/exec-*.json` / `base_commits_*.json` or the builds around late_commit's merge time (±~150 ids), and pass it as `--build-range lo-hi`. Keep the range under ~300 ids.
3.5. **Determine the callstack depth of the conflict.** Read the full traceback from `RUN_DIR/full_error_<slug>.json` (or re-fetch it with `fetch_full_error.py` if evidence wasn't handed to you). Count frames from the outermost failing test function down to the deepest frame that references the conflicting call/attribute - e.g. `test_msa_buffers_stage_local_cache_views -> msa_idx_k_cache -> get_index_k_buffer` is depth 2 (two hops from the test). If the traceback is thin (a bare `AssertionError`/`AttributeError` with only the test frame), read the actual diff hunks of `early`/`late` instead and count the real call chain between the test's entry call and the line each side touches. Note the depth and the frame chain for step 4.
4. **Run the measurement:**
   ```bash
   python3 <skill_dir>/semantic_failures_analysis.py --entity '<E1>' [--entity '<E2>' ...] \
     --early <sha> --late <sha> [--fix <sha>] (--build-range <lo>-<hi> | --last-build <id>) \
     --label <LABEL> --platform <PLATFORM> \
     --callstack-depth <N> --callstack-summary '<frame -> frame -> frame>' \
     --out RUN_DIR/semantic_<LABEL>.json --stats-file ./semantic_failures_stats.jsonl
   ```
   It resolves PR numbers, PR open time and time-to-merge via GitHub, finds last_build and base_commit via ci_report + GitHub compare (or reuses the OpenSearch-resolved `--last-build` from step 2), computes the gaps, records `callstack_depth`/`callstack_summary` from step 3.5 verbatim into every entity's record, writes the JSON and appends one deduplicated JSONL record per entity. Every duration is reported both as numeric `hours` (for statistics) and as `duration` = `x days x hours x minutes` (use the latter in prose and tables). If you genuinely can't determine a depth (no traceback, diff too indirect to count hops), omit both flags rather than guessing - `callstack_depth` stays `null` in the record.
5. **Validate that the timeline actually supports the conflict theory before writing anything up.** `semantic_failures_analysis.py`'s output JSON already carries every timestamp needed - `records[].base_commit.merged_at`, `records[].early_commit.merged_at`, `records[].late_commit.merged_at`, `records[].last_build_of_late_pr.created`, `records[].relations.base_to_early.{hours,early_already_in_base}` - don't skip this because the script ran cleanly; a clean run can still encode an impossible or misleading order:
   - **`base_commit.merged_at` before `early_commit.merged_at`?** (equivalently: `relations.base_to_early.hours` positive and `early_already_in_base` false). This is the load-bearing check. If true, `last_build` genuinely could not have exercised `early_commit` - the "stale base" story holds. If **false** (`early_already_in_base: true`), the base already contained `early_commit` when B's own CI ran, so B's CI *should* have hit the conflict and didn't - stop calling this a stale-rebase gap and go find why (stage skipped/reused, test not collected, a flaky pass) via last_build's stage in ci_report `tests_by_stage`; the finding becomes a CI gap, not a timing gap.
   - **`early_commit.merged_at` before `late_commit.merged_at`?** The script already enforces this at the top of `main()` (it swaps early/late and prints `note: --early merged after --late; swapping` to stderr if violated) - just confirm that note didn't fire for the wrong reason (i.e. you didn't accidentally pass the two shas backwards and get a silent, correct-looking swap that masks a wrong pair).
   - **`last_build_of_late_pr.created` before `late_commit.merged_at`?** Sanity check that the build which gated the merge actually ran *before* the merge, not a stray post-merge re-run mistakenly picked up in step 2. A violation means step 2 picked the wrong build - go back and pick the newest OpenSearch hit strictly before the merge timestamp.
   - **`base_commit.merged_at` before `late_commit.merged_at`?** Should be trivially true; a violation means `base_commit` was resolved against the wrong build or the wrong PR entirely - re-run `get_base_commit.py` and confirm `head_commit` matches `last_build_of_late_pr`'s tested head.
   If any of the last three fail, the record is not trustworthy - fix the input (right build/commit/labels) and re-run before writing `semantic_<LABEL>.md`, don't rationalize around it.
6. **Interpret** (write `RUN_DIR/semantic_<LABEL>.md`):
   - State the pair, what each side changed (one line each, file:line from the error), and the fix.
   - Table of the gaps (`duration` as `x days x hours x minutes`, plus commit counts) **and the four checkpoint timestamps in merge order** (`base_commit.merged_at`, `early_commit.merged_at`, `last_build_of_late_pr.created`, `late_commit.merged_at`) so a reader can see the sequence holds at a glance. If `early_already_in_base` is true, look at last_build's stage for the failing test in ci_report `tests_by_stage` and explain why it passed (skipped "Reused from previous pipeline", not collected, or a genuine pass = flaky assertion) - that changes the lesson from "stale base" to "CI gap". If `base_commit` predates `early_commit` itself, say so explicitly - it means B's last CI run couldn't structurally have exercised the conflict at all (not just "was stale"), which is a stronger finding than a normal rebase gap.
   - Per commit: sha, PR, author, PR opened, merged, time-to-merge, commits/files in the PR.
   - **Callstack depth**: state `callstack_depth` and the frame chain (`callstack_summary`) from step 3.5, and read it alongside the timing gaps rather than in isolation - a shallow depth (1-2) with a short `early→late` gap suggests the conflict was easy to miss only because of timing (a rebase would have caught it); a deep depth suggests it would have been hard to catch even with a rebase, strengthening the case for a required integration test over the specific interaction rather than just "rebase more often".
   - One-line lesson: e.g. "B's CI base was 0 days 23 hours 10 minutes / 41 commits old and predated A by 0 days 12 hours 5 minutes; a rebase-before-merge check or a required post-rebase CI run would have caught it."
7. **Report back**: the table, the checkpoint timestamps and whether they held, the callstack depth/chain, the lesson, the paths (`semantic_<LABEL>.json`, `.md`, the stats file line count), and anything that did not resolve (PR not found for a commit, no build before merge in the range - then widen once).

## Pitfalls
- Using the PR's `baseRefOid` or the PR branch point as base_commit; only the tested head's merge-base counts.
- Choosing the wrong "late" commit: the late commit is the one whose merge broke `main`, which is not always the one that touched the failing test file.
- Scanning thousands of ci_report builds; try the OpenSearch `stage_info` lookup (step 2) first, and only fall back to a bounded `--build-range` scan when that doesn't resolve.
- Counting a fixture-only fix as "the interface was reverted" - record `late_to_fix` but describe what the fix changed.
- Time zones: GitHub and ci_report `ts_created` are UTC; dashboard per-execution `ts` is US-Pacific-as-epoch.
- Accepting the script's gap numbers without checking they describe a possible sequence (step 5): a `last_build` that actually ran *after* `late_commit` merged, or a `base_commit` newer than `late_commit`, means the wrong build/commit was resolved - the gaps will still compute (and look plausible) but describe a timeline that didn't happen.
- Treating a `SUCCESS` stage as proof the case ran: check `test_info` for the case itself (step 2) - a passing stage with the case `SKIPPED` or absent from the roll-up is not evidence of a clean build, it's an unverified build wearing a green checkmark.
- Counting callstack depth from the short error message instead of the real traceback: `short_error_msg`/`s_short_error_msg` usually gives only the raising line, not the calls above it - use the full traceback (`full_error_<slug>.json`) or the diff-derived call chain, and say which source the depth came from.
- Assuming a plausible-looking `early`(test-add) x `late`(breaker) pair is a real conflict without step 0's check: if the test-introducing commit had already been green on `main` for days before the candidate `late` commit merged, there's no interaction to measure - it's a plain regression wearing a semantic-conflict costume because a test just happens to be the victim.
